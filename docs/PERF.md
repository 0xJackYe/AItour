# 性能测试报告

测试日期：2026-11-08　|　Node 22　|　Chromium 153（Playwright）　|　复现：`npm run build && npm run perf`

## 一、结论

- **服务端不是瓶颈。** 一次规划中，本项目自身代码的耗时是毫秒级：3 天行程约 2–6 ms，30 天行程约 11–16 ms。用户等待的 20–40 秒几乎全部是大模型推理和 Google 接口的网络时间。
- **并发保护有效。** 8 个并发（等于默认并发上限）持续请求时，64/64 全部成功，进程 CPU 占用不到 5%。40 个请求同时到达时，8 个正常处理，其余 32 个在 42 ms 内（p95）收到“服务繁忙”，不会排队拖垮服务。
- **没有内存泄漏。** 连续 300 次规划后，强制 GC 后的堆内存稳定在 15.2–15.6 MB，Google 缓存条目数有上限。
- **前端轻量。** 首次加载约 73 KB（gzip，JS 68 KB + CSS 5 KB）。桌面首屏 0.1 秒；手机在 CPU 降速 4 倍、慢速 4G 的条件下首屏 1.6 秒。
- **超长行程也流畅。** 30 天、11 座城市、170 个地点的行程，桌面 0.17 秒渲染完成，没有长任务；限速手机 0.65 秒完成，总阻塞时间 75 ms。切换城市、某一天和总览都在 50 ms 以内。

## 二、测试方法

上游的大模型和 Google 地图都用项目自带的模拟服务（`server/testing/mockUpstream.js`），这样测到的是本项目自身代码的开销，不含真实网络和模型推理。脚本在 `perf/run.mjs`，结果另存为 `perf/results/<时间>.json`。

| 部分 | 内容 |
| --- | --- |
| 服务端流水线 | 4 个场景：京都 3 天、北海道 5 天（多城市）、京都 14 天和 30 天（分段生成）。上游零延迟，每个场景跑 12 次，分别测“冷缓存”（每次清空 Google 缓存）和“热缓存” |
| 确定性步骤 | 30 天多城市行程上逐项计时：规范化、顺序优化、城际交通推断、排程、序列化 |
| HTTP 并发 | 模拟上游延迟：大模型每次 800 ms，Google 每次 40 ms。分两种情况：8 个客户端各连续请求 8 次；40 个请求同时到达 |
| 内存 | 连续 300 次规划（4 种需求轮换），每 100 次强制 GC 后记录内存 |
| 前端 | 生产构建。分桌面和“手机”（CPU 降速 4 倍、慢速 4G：150 ms 延迟、1.6 Mbps）两种条件，测首屏、30 天多城市行程的渲染和视图切换 |

前端测试使用记录调用的轻量地图桩，测的是本项目代码的开销，不含 Google 地图自身的绘制时间。

### HTTP 并发

| 情况 | 成功 | 拒绝 | 吞吐 | 延迟 p50 / p95 | 进程 CPU |

| 8 个并发 × 8 次 | 64 | 0 | 4.96 次/秒 | 1608 / 1632 ms | 4.4% |
| 40 个同时到达 | 8 | 32（503） | — | 成功：1620 ms；拒绝 p95：42 ms | — |

在模拟延迟下，一次规划要依次调用两次大模型（生成和自审），理论下限约 1600 ms，实测 p50 为 1608 ms，本项目代码只增加了约 8 ms。吞吐量由并发上限（默认 8）和上游速度决定，提高 `PLAN_MAX_CONCURRENT` 即可线性扩展。

## 四、测试中发现并修复的问题

第一轮前端测试发现，长行程在限速手机上不够流畅，修复如下：

| 指标（手机，限速） | 修复前 | 修复后 |
| --- | --- | --- |
| 30 天行程渲染的总阻塞时间 | 384 ms | 75 ms |
| 最长任务 | 329 ms | 94 ms |
| 回到总览 | 302 ms | 42 ms |

改动：

- 所有天保持挂载，切换视图只改 `hidden`，不再重建整段列表；
- 每天的组件用 `memo`，属性引用保持稳定；
- 新结果放进 React transition 分片渲染；
- 屏幕外的天使用 `content-visibility: auto`，跳过布局和绘制。

## 五、部署提示

- **Cloudflare Workers 的 CPU 时间。** 免费版每次请求的 CPU 上限是 10 ms（等待网络的时间不算）。上表 CPU 列是包含模拟上游开销的上限值：3 天行程热缓存下约 3 ms，30 天冷缓存下约 22 ms。短行程基本在免费额度内，长行程可能超出。正式上线建议使用付费版（默认 30 秒，可以在 `wrangler.jsonc` 的 `limits.cpu_ms` 里调整）。
- **并发与限流。** 单实例默认最多 8 个同时规划、每个 IP 每 10 分钟 20 次（Cloudflare 配置为 15 分钟 10 次）。限流和缓存都是单实例内存实现，多实例部署时需要换成共享存储（见 [REVIEW.md](./REVIEW.md) 路线图）。
- **没有测到的部分。** 真实大模型推理和 Google 接口的延迟，取决于上游服务和网络。这次测试期间 DeepSeek 账户余额不足，无法用真实模型测完整耗时；上一轮真实评测中，短行程约 20–40 秒，见 [EVAL.md](./EVAL.md)。
