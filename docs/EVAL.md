# 行程质量评测报告

评测日期：2026-11-07　|　模型：`deepseek-chat`（DeepSeek V4.1-Flash 非推理模式）　|　评测集：`eval/cases.json`（12 个用例）

## 一、结论

**问题：** 生成的行程能不能成为人可以直接照着走的、完整、详细、易读的旅游方案？

**改进前：** 方案“对”，但“不能用”。地点真实、天数完整、用户点名的地点全部覆盖，路线也大体顺路。问题在于：没有一个地点有时间；每个地点的介绍只有十几个字；11 个行程里只有 1 个每天都安排了吃饭；没有费用、预算和预订提醒。读完只知道“去哪”，不知道“几点去、怎么吃、花多少、要不要提前订”。

**改进后：** 同一套评分规则下，通过率从 **66%（132/199）提升到 98%（196/199）**，正确性没有任何回退。每个地点都有到达时间、停留时长、费用和具体看点，每天安排午餐和晚餐（具体到店名），换城市的日子写清车次与车程，并给出人均预算、提前预订清单和每个过夜城市的住宿与参考价。

可以直接阅读的真实输出（未经人工修改）：

- [京都 3 天](./samples/kyoto-3d.md)
- [带父母去杭州的周末](./samples/hangzhou-weekend-elderly.md)：针对“老人腿脚不太好”，主动选择平路、游船、有电梯的景点和餐厅
- [塞尔维亚 → 法国 28 天](./samples/europe-28d.md)：六国、128 个地点，每个地点都有时间

**代价：** 短行程生成时间从约 10 秒增加到 20–40 秒（内容约多一倍）；生成过程有实时进度显示，用户可以随时停止。

## 二、评测方法

### 用例

12 个真实风格的需求，覆盖不同的难点：

| 用例 | 难点 |
| --- | --- |
| 京都 3 天、东京亲子 5 天、巴黎 4 天、成都美食 3 天 | 前端自带的 4 个示例 |
| 日本两周（东京、京都、大阪、奈良） | 长行程、多城市 |
| 塞尔维亚 → 法国 28 天，六国，火车 | 超长行程、跨国、指定起点终点与交通方式 |
| 新疆北疆自驾 10 天 | 自驾、长距离、季节性道路 |
| 周末带爸妈去杭州 | 老人、节奏轻松 |
| 5 days in New York（英文） | 英文输入 |
| 上海一日 citywalk | 一日游、步行 |
| 曼谷穷游 4 天 | 预算偏好 |
| “想出去玩几天，有什么推荐” | 信息不足，应先澄清 |

### 评分规则（`eval/run.mjs`）

每个用例自动检查以下项目：

- **正确性**：
  - 生成成功，天数完整无空白；
  - 用户点名的地点、城市、国家全部覆盖，跨国行程的起点和终点正确；
  - 识别出节奏、交通、预算偏好；
  - 信息不足时先澄清。
- **节奏**：每天主要地点的数量或总时长符合节奏偏好；全天型景点（停留 ≥5 小时）和换城市的日子允许只有一处。
- **详细度**：
  - 每天时间连贯递增；
  - 90% 以上地点的介绍不少于 25 字；
  - 70% 以上地点有实用提示和费用信息。
- **可执行性**：
  - 每天有午餐和晚餐（换城市日、最后一天、全天型景点日允许只有一顿）；
  - 每天有交通建议；
  - 住两晚以上的城市都有住宿建议；
  - 有人均预算、提前预订提醒、实用贴士和路线思路。

评分规则在过程中调整过两处：节奏由“只看地点数量”改为“数量或总时长”，住宿由“每个城市”改为“住两晚以上的城市”。原因是人工审阅发现，citywalk（很多短站）、两个大型商场或市场组成的一天，以及中途的一日游城市（如奈良），原来的规则会误判。**改进前后的结果都按最终规则重新计分，口径一致。**

### 运行条件

- 大模型：真实 DeepSeek API，提示词版本 `2026-11-07.4`。
- Google 地图校验：**未启用**。评测环境中没有 Google Key，因此地点核实、逐段路线和交通站没有参与评测。这几部分由带模拟上游的集成测试和浏览器测试覆盖。
- 每个用例只跑了一次。大模型输出有随机性，单次结果有一定波动。

## 四、人工审阅发现与对应改动

逐份阅读输出后发现的问题，以及对应的改动：

| 发现 | 改动 |
| --- | --- |
| 没有时间，读者不知道几点该在哪；28 天行程中 8 小时的火车只出现在一行备注里 | 每个地点增加 `start_time`。服务端校验格式与先后顺序，缺失或乱序时按停留时长和路上时间重新推算；有 Google 真实路程时，赶不到的那一站会顺延 |
| 介绍只有十几个字 | 介绍要求 40–80 字，写清看什么、做什么、吃什么；原来“文字简短”的限制是为旧模型 8K 输出上限设的，现已提高到 16K |
| 多数天没有吃饭的安排 | 每天安排午餐和晚餐（具体店名）；长行程由细化阶段按当时所在位置补充 |
| 长行程 32 家餐厅里有 31 家名为“?” | 骨架阶段不再列餐厅；规范化层丢弃“?”“待定”“午餐”之类的占位名称 |
| 细化质量因分段而异，有的段落缺餐、介绍过短 | 新增确定性质量闸门：逐天检查介绍长度、午晚餐、时间和交通建议，不达标的天再定向细化一次，且只在结果更好时才采用；细化分段从 5 天缩小到 3 天 |
| 要求“不要编造”后，模型几乎每条提示都写“以官方信息为准” | 改为：著名景点的开放时间和门票直接写出，确实不确定的才省略 |
| 编造了“清水寺需预约时段票” | 增加“只写有把握的事实”规则（仍无法完全杜绝，见下文） |
| 长行程的 AI 自审因输出超过 2048 token 被截断，自审被静默跳过 | 自审输出上限提高到 6144，并要求精简 |
| 有交通建议的说明但没有费用、预算和预订信息 | 增加每站费用、人均预算（分项之和自动校验）和提前预订清单 |

界面上的对应改动：

- 每站显示时间和费用；
- 住宿、预算和预订合并成一张“出发前准备”卡片；
- 新增“复制行程文字”（可直接粘贴到微信或备忘录）和“打印 / 存为 PDF”。

## 五、仍然存在的问题

1. **事实准确性无法自动保证。** 例如样例中“圣马可大教堂免费但需预约”，该教堂现已收费。开放时间、票价、预约规则都可能过时或不准，界面和导出文档末尾都有“出发前请再次确认”的提示。根本的解法是接入 Google Places Details 的营业时间，以及官方票务数据（见 [REVIEW.md](./REVIEW.md) 路线图 C）。
2. **少数天仍缺一顿饭。** 本次评测中，东京亲子有 1 天、纽约有 2 天缺少其中一顿；东京迪士尼当天写的是“乐园内快餐”这样的泛称。提示词已要求园区内也写具体餐厅，质量闸门也会补充缺餐的天，但都是概率性的改进。
3. **上海 citywalk 缺少当天交通建议。** 已把“缺少交通建议”加入质量闸门。
4. **最后三处小改动未用真实接口复测。** 包括：交通建议加入质量闸门、园区内餐厅写具体名称、住宿提示只针对住两晚以上的城市。这三处都有单元测试覆盖；原因是最后一次完整复测时，DeepSeek 账户返回“余额不足”（HTTP 402）。
5. **地图校验未参与本次评测**（没有 Google Key）。地点核实、逐段交通方式与时间、按真实路程顺延时间等，需要配置 Key 后再跑一次评测确认。

## 六、成本

本轮所有评测与调试共调用大模型 153 次，消耗约 20 万输入 token 和 29 万输出 token。

改进后单个行程的输出 token 大约增加一倍；长行程的定向补充会额外增加 1–4 次调用。可以从每个响应的 `meta.stats` 中按请求统计成本。

## 七、如何复现

```bash
DEEPSEEK_API_KEY=你的Key npm run eval
```

```bash
DEEPSEEK_API_KEY=你的Key npm run eval -- --cases kyoto-3d,europe-28d --label 对比
```

```bash
npm run eval -- --rescore eval/results/<某次结果目录>
```

- 配置 `GOOGLE_MAPS_API_KEY` 后会同时评测地图校验和路线。
- `--rescore` 不调用大模型，只用当前评分规则重新计分。
- 结果在 `eval/results/<时间>-<label>/`，包括每个用例的 JSON、可读的 Markdown 行程和汇总报告。
