# AItour 项目审查与商业化路线图

审查日期：2026-11-07　|　审查范围：全部前后端代码、提示词、测试与工程配置

## 一、结论

AItour 的方向是对的：采用“大模型出结构化数据 → 地图服务落地 → 前端渲染”的架构，没有让大模型直接操作界面或编造坐标。这在同类 MVP 里属于正确的工程选择。

但离“稳定可靠、可以商用”还有明显差距，主要集中在三点：

1. **输入理解不可靠。** 天数识别只支持阿拉伯数字，前端自带的 4 个示例全部识别失败。
2. **地点校验过严。** 城市边界规则会把用户点名的近郊地点删掉，比如凡尔赛宫和东京迪士尼。
3. **调用链路没有韧性。** 没有重试、没有进度，部分调用没有超时，用户离开后仍在继续花钱。

前端的问题是信息层级平铺：6 个面板堆在左栏，用户需要自己拼出“今天去哪、怎么去”。

本次已完成的工作：

- 重构生成链路，让同一个需求每次都能得到**完整、可核实、路线合理**的结果，失败时也有明确、可重试的错误；
- 把界面收敛为“一个输入框 + 一条时间线”，核心功能一个不少；
- 补齐 127 项自动化测试（服务端 113 项、前端 10 项、浏览器端到端 4 个场景）和 CI。

下一阶段的重点：异步任务化与多模型容灾、质量评测体系、行程编辑与分享、可观测性和成本控制。详见第四节。

## 三、本次优化

### 1. 稳定可靠地生成路线

整条链路的设计原则是：**每一步都可校验，每个失败都有降级，任何情况下质量只升不降。**

```text
需求解析（确定性）
  ├─ 天数：中英文数字 / 周 / 月 / 晚 / 分段求和；含糊表述（“两三天”）只作参考
  ├─ 交通偏好：自驾 / 步行为主
  └─ 超过 30 天 → 直接澄清，不消耗额度
生成（大模型）
  ├─ ≤7 天：单次生成；被截断 → 自动降级为分段生成
  ├─ ≥8 天：完整骨架 + 每 5 天一段并行细化（细化失败保留骨架）
  ├─ 缺天 / 空白天 → 只针对这些天定向补全（最多两轮）
  └─ 传输层：流式 + 总超时 + 空闲超时；429/5xx/网络错误退避重试；取消立即中止
校验（并行）
  ├─ AI 自审：覆盖度 / 准确性 / 节奏
  └─ Google 核实：都市圈半径 + 视口 + 行政区 + 名称（含简繁、日文汉字）+ 一日游距离上限
重生成（至多一次）
  └─ 触发：自审发现主体问题，或 ≥25% 地点无法核实 → 带具体反馈重生成 → 两版择优
路线
  ├─ 当日顺序优化（餐厅、有时段要求的地点不动；节省 ≥20% 且 ≥1km 才采用）
  ├─ 逐段交通：≤1.5km 步行；更远公共交通（自驾偏好则驾车），逐级回退，最后直线兜底
  └─ 住宿附近交通站（每个城市分别查询）
```

关键机制和对应代码：

| 机制 | 解决的问题 | 位置 |
| --- | --- | --- |
| 确定性需求解析 + 硬约束注入 | 天数识别错误、模型忽略天数 | `server/services/intent.js`、`prompts.js` |
| 字段白名单规范化 + 完整性校验 | 模型输出类型错、缺字段、重复天、跳号 | `server/services/planSchema.js` |
| 截断降级 + 定向补全 | 长行程失败、缺天 | `server/services/llm.js` |
| 流式 + 空闲超时 + 重试 | 上游卡死、限流、抖动 | `server/services/llm.js`、`lib/async.js` |
| 分层地点核实 + 基准城市回退 | 外地同名地点、近郊地点误删、模型标错城市 | `server/services/geocode.js` |
| 缓存 + 并发闸门 + 重试 | 配额、费用、延迟 | `server/services/google.js`、`lib/cache.js` |
| 校验驱动的重生成 + 择优 | 幻觉地点、质量回退 | `server/services/pipeline.js` |
| 逐段多模式路线 | “步行 2 小时”的不合理路线 | `server/services/route.js` |
| 保守顺序优化 | 当天折返 | `server/services/optimize.js` |
| SSE + 心跳 + 断开即取消 + 总时长上限 | 代理超时、无进度、白花钱 | `server/routes/plan.js`、`lib/sse.js` |

### 2. 前端：更简单，核心功能不变

改版前左栏依次堆叠：输入面板、解析结果（7 格网格）、自审面板、交通点位、计划面板（含住宿卡、日期标签、日程卡、贴士）。改版后是一条从上到下的阅读流：

```text
输入框（示例只在首次出现；生成中按钮变为“停止”）
→ 进度（四个阶段 + 当前动作 + 取消）
→ 行程标题与概况标签（城市 · 天数 · 节奏 · 预算 · 兴趣）
→ 一行质量结论（例如“9/9 个地点已在 Google 地图上核实”，有问题才可展开）
→ 住宿建议（含附近站点）
→ 按天筛选（吸顶）
→ 每天一条时间线：地点 → 交通方式与时长 → 下一个地点（点击联动地图，一键导航）
→ 路线思路、实用贴士（折叠）
```

原有功能的去向：

| 原功能 | 现在的位置 |
| --- | --- |
| 自然语言输入、示例、重新生成 | 输入框（示例为一行标签） |
| 解析结果面板 | 行程标题下的概况标签 |
| 澄清问题、错误与重试 | 输入框下方的提示卡（错误带请求编号） |
| 自审结果、地理编码警告 | 一行质量结论，可展开明细 |
| 交通点位面板 | 住宿建议中的“附近站点” + 地图标记 |
| 住宿推荐、每日主题、景点详情、交通建议、实用贴士 | 住宿卡 + 时间线 + 折叠区 |
| 地图标记、路线、信息窗口、按天筛选 | 保留；新增点击地点联动、每日一键导航 |
| 本地历史 | 右侧抽屉（兼容旧记录） |

视觉上采用 Material 3 风格的设计令牌（色板、圆角、间距、阴影集中在 `:root`），列表与地图共用一套每日配色，文字对比度满足 WCAG AA。键盘可以完成全部操作（Ctrl+Enter 生成、Esc 关闭抽屉）。移动端地图吸顶，行程在下方滚动。

### 3. 工程化

- **测试**：服务端 113 项（含真实 Express + 模拟上游的 HTTP 集成测试，覆盖重试、截断降级、补全、重生成择优、取消、限流、并发、降级等），前端 10 项，Playwright 端到端 4 个场景（桌面完整流程、错误/澄清/取消、移动端、地图不可用）。端到端测试发现并修复了一个只在真实浏览器中出现的问题：点击“停止”后按钮在同一次点击中变成提交按钮，导致重新提交。
- **CI**：GitHub Actions 在推送和 PR 时运行全部测试与构建。
- **配置**：集中在 `server/config.js`，全部可通过环境变量调整（见 `.env.example`）。
- **部署**：`npm run build && npm start` 单进程同时托管前端与 API；`/api/health` 可用于健康检查。
- **可观测性（基础版）**：结构化日志（生产环境输出 JSON），每个请求带 `X-Request-Id`；响应中的 `meta.stats` 记录大模型调用次数、token 用量和 Google 调用次数，可直接用于成本核算。

## 四、对标企业级标准：后续路线图

下面按 Google 内部评审常用的维度列出差距。按计划，登录与支付由业务侧自行接入，这里只列出需要为它们预留的接口。

### A. 可靠性与 SRE

- **定义 SLO 并监控**，建议起点：
  - 规划成功率 ≥ 99%（不含用户取消与澄清）；
  - 7 天以内行程 P95 时延 < 90 秒；
  - 地点核实率 ≥ 90%；
  - 逐日完整率 100%。
- **异步任务化**：把生成改为后台任务（Cloud Tasks / Pub/Sub + Cloud Run Jobs）。前端拿 `jobId` 订阅进度，刷新页面或断网后可以恢复；顺带实现幂等（相同用户 + 相同需求短时间内复用结果）。
- **固定模型版本**：截至 2026 年 11 月，`deepseek-chat` 已是 `deepseek-flash`（V4.1-Flash）非推理模式的别名，别名随时可能下线或变更。建议显式配置模型，并在每次换模型前跑一遍评测集。
- **多模型容灾**：主备两个 OpenAI 兼容服务（如 DeepSeek + Qwen/Gemini），加熔断器和按健康度路由。目前已支持任意 OpenAI 兼容 Base URL，补一个“备用提供方”配置即可起步。
- **共享状态外置**：限流、缓存、并发计数迁到 Redis（Memorystore），支持多实例水平扩展。
- **故障演练**：定期注入上游超时、429、坏 JSON，验证降级路径。测试中的模拟上游已经支持这些故障注入。

### B. 质量评测（LLM Ops）

这是从“能用”走到“可靠”的关键，也是成熟团队和 MVP 的最大差别。

- **黄金评测集**：已经建立第一版（12 个用例，`npm run eval`，结果见 [EVAL.md](./EVAL.md)）。下一步扩充到 100–300 条，覆盖单城、多城、长行程、亲子、自驾、模糊需求和多语言等真实需求，并启用 Google 地图校验一起评测。
- **自动指标**：
  - JSON 失败率、逐日完整率、地点核实率；
  - 点名地点覆盖率、折返率、节奏符合度；
  - 单次成本、P50/P95 时延。
- **回归门禁**：每次改提示词或换模型都跑评测集出报表，指标下降不允许上线。提示词已集中在 `prompts.js` 并带 `PROMPT_VERSION`，可以直接接入。
- **线上反馈闭环**：对每天、每个地点提供“👍/👎/地点不对”的一键反馈，抽样人工评审，问题样本回流到评测集。
- **更强的结构化输出**：模型支持 JSON Schema 严格模式时启用，进一步降低格式错误。

### C. 地图与数据能力

- **日本等地区的公共交通数据**：Routes API 在日本不返回公交方案（草稿 PR #1 已用真实 Key 确认）。目前的处理是诚实降级：近距离步行、远距离打车参考并明确标注，导航链接以公交模式打开 Google 地图。要在应用内展示真实的电车线路与换乘，需要接入当地数据源，例如 NAVITIME 或乗換案内类 API。
- **营业时间感知排程**：用 Places Details 获取 `regularOpeningHours`，避开闭馆日、按开放时段排序。这是目前最影响“可执行性”的缺口。
- **更丰富的地点信息**：评分、价格等级、照片，前端可展示缩略图。
- **跨城交通**：用火车/航班分段数据替代纯道路路线，多国长线尤其需要。
- **预算估算**：门票、交通、住宿、餐饮按天汇总，与用户预算对比。
- **中国大陆市场**：Google 地图在大陆无法访问。如果目标用户在大陆，需要把地图服务抽象成 Provider 接口，接入高德或腾讯地图，并处理 GCJ-02 坐标系。建议尽早决定目标市场，因为这会影响前后端多个模块。
- **合规**：遵守 Google Maps Platform 条款。坐标缓存不超过 30 天（当前默认 12 小时），Places 数据须在 Google 地图上展示，保留署名。

### D. 产品功能（不含登录 / 支付）

按商业价值排序：

1. **行程编辑**：拖拽调整顺序、增删地点、“换一个”单个地点、单天重新生成、锁定地点后重排。
2. **分享与导出**：只读分享链接、导出 PDF / 日历（ICS）、发送到手机。分享链接需要服务端存储，可与账号体系一起设计。
3. **对话式微调**：例如“第二天轻松一点”“把美食换成素食”，在现有计划上增量修改，而不是整份重来。
4. **多语言**：界面与生成内容支持中 / 英 / 日。
5. **离线可用（PWA）**：出行途中网络差时仍可查看行程。

需要为登录和支付预留的接口：

- 按用户的配额与限流（当前为按 IP）；
- 计划归属与云端同步（当前只存本地 IndexedDB）；
- 用量计费的数据来源（`meta.stats` 已提供 token 与地图调用数）。

### E. 安全、隐私与合规

- 密钥放入 Secret Manager；浏览器 Key 与服务端 Key 分离，分别限制 Referrer、IP 与 API 范围（文档已说明，代码已支持）。
- 内容安全策略（CSP，需放行 Google Maps 相关域名）、依赖漏洞扫描（Dependabot / `npm audit`）、WAF / Cloud Armor 防刷。
- 用户输入可能包含个人信息（同行人、行程日期），需要日志脱敏、数据保留期限和删除机制，满足 PIPL / GDPR。
- 生成内容的安全审核，以及提示词注入防护。目前已有输出字段白名单，大模型也没有工具权限，风险较低。

### F. 可观测性与成本

- 接入 OpenTelemetry：为每个阶段（生成、自审、核实、路线）建 span，上报 Cloud Trace / Monitoring，按阶段看时延分布。
- 指标看板：成功率、错误码分布、核实率、缓存命中率、单次成本，并设置告警阈值。
- 前端监控：Web Vitals 与错误上报（如 Sentry）。
- 成本优化方向：
  - 短行程在地图核实全部通过时跳过自审，或改用小模型做自审；
  - 利用 DeepSeek 前缀缓存，把系统提示词放在消息最前且保持稳定，目前已满足。

### G. 工程与交付

- 迁移到 TypeScript，用一份 schema（zod / JSON Schema）同时约束大模型输出、后端接口和前端类型。
- 环境分层（dev / staging / prod）、Feature Flag、灰度发布；容器化部署到 Cloud Run（无状态、自动伸缩、保留最小实例避免冷启动，请求超时调到 ≥ 10 分钟以支持 SSE）。
- 数据库：Cloud SQL（Postgres）或 Firestore，存储用户、计划、分享与反馈。
- 统一代码规范：ESLint + Prettier + 提交前检查。

## 五、建议的里程碑

| 阶段 | 周期 | 目标 |
| --- | --- | --- |
